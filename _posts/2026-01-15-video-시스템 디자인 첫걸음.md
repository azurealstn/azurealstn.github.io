## 강의 소개

![시스템 디자인 첫걸음: 면접에서 돋보이는 백엔드 아키텍처 설계하기](/assets/images/시스템%20디자인%20첫걸음.png)

대규모 백엔드 시스템을 어떤 기술과 어떻게 설계할 수 있는지, 트레이드오프를 고려한 기술적 의사결정과 실제 서비스에서 사용되는 주요 기술 등을 배울 수 있습니다. 간단한 프로젝트라도 설계없이 코드만 작성한다면 몇달지나서 유지보수하기 힘든 코드를 맞닥뜨릴 수 있습니다. 그래서 기본적인 백엔드 시스템에 대한 학습을 하고 나면 그 코드에 고민을 드러내어 좀 더 나은 시스템을 만들 수 있을 것입니다. 정리할 때 키워드 위주로 정리하였고, 시스템을 설계하기 전에 정리된 자료를 참고하면 좋을 것 같습니다

## 잘 만든 시스템의 기준

- 목표를 얼마나 달성했는가
- 신기술 X
- 최신 아키텍처 X
- 많은 유저를 모으고 잡아둘 수 있는 서비스를 만들어 수익 창출 O
- 만드려는 서비스에 따라 목표가 달라질 수 있다

> 지금 이 순간 주요 목표에 가장 적합한 아키텍처를 선택하는 것, 즉 아키텍처에 정답은 없다

### 신뢰성 높이기

- 사용자가 예상한대로 기능을 수행한다 -> 정확성/정합성
  - 요구사항 분석
  - 테스트 작성
  - 트랜잭션 관리
  - 상태 일관성
- 무언가 잘못되어도 정확하고 일관되게 동작한다
  - 백엔드에서의 검증, 예외처리
  - 멱등성
  - 분산 트랜잭션 처리
  - 재시도
  - Circuit Breaker
- MTBF, MTTR, 에러율, 데이터 무결성 검사
- 동일한 요청이 여러번 들어와도 데이터 정합성을 위한 설계 필요

### 성능 높이기

- 기능이 얼마나 빨리 동작하는가?
  - 시스템이 주어진 자원 내에서 사용자 요청에 빠르고 안정적으로 반응하는 특성
  - 금융 같은 돈에 민감한 서비스는 특히 성능을 잘 고려해야 한다
- 데이터 캐싱
  - Redis
  - 캐시 라이브러리
  - CDN
- 비동기 처리
- DB 최적화
  - 인덱스
  - 쿼리 튜닝
  - 샤딩
  - 복제
- 아키텍처 개선
  - CQRS
  - 이벤트 기반
  - MSA
- 이러한 성능을 높이는 방식중에는 항상 트레이드오프가 있으므로 고민을 많이 해봐야한다 성능을 높일수록 그만큼 복잡성이 늘어난다
- 이력서를 적을 때도 이러한 성능 개선에 대해 자세하게 적어주면 좋다. (데이터 단위로 명시)

### 가용성

- 시스템을 언제든지 사용할 수 있는 상태로 유지하는 특성
- 단일 장애 지점(SPOF)이 없어야한다
- 장애가 발생할 수 있는 컴포넌트에서 빠르게 복구할 수 있어야 한다
- 서버 이중화
- 재시도 및 실패 대비 설계
- 장애감지 (헬스체크)

### 확장성

- 트래픽이나 데이터가 증가해도 시스템이 성능을 유지하며 잘 동작할 수 있는 특성
- 서버를 늘리는 것만으로는 한계가 있기 때문에 성능도 같이 고민해야 한다

## 주요 시스템 컴포넌트

## 서버와 서버 간 통신

- 서버란 데이터를 가져와서 비즈니스 로직에 따라 가공하여 사용자에게 응답하는 구조
- WEB 서버
  - Nginx, Apache
- WAS
  - Tomcat, Jetty
- 규모가 작다면 WAS로도 가능하지만 점점 규모가 커질수록 앞에 WEB 서버를 두어 좀 더 유연하게 대처할 수 있다
- 도메인 별로 서버 분리하기 (모놀리식 -> MSA)
- 통신 방식
  - REST API
  - gPRC
  - 이벤트 기반 비동기 통신
  - GraphQL
  - WebSocket
- 신뢰성 있는 서버 통신을 위한 전략
  - 타임아웃 & 재시도 처리
  - 서킷 브레이커
  - 멱등성

## API 게이트웨이

- 로드밸런서: 로드밸런서에 서버를 추가해주면 로드밸런서가 알아서 트래픽을 분산시킬 수 있으면 유연하게 서버를 증설할 수 있다는 장점이 있다
  - 라운드 로빈
  - Least Connection
  - IP Hash
- API 게이트웨이: 여러 백엔드 API 앞에 있는 단일 진입점(Front Door) 역할을 하는 컴포넌트이다. 클라이언트는 개별 서비스가 아닌 API 게이트웨이 하나만 호출하면 게이트웨이가 중간에 내부 서비스들과 통신을 중계한다
  - Kong
  - Nginx
  - Spring Cloud Gateway
- 서비스 디스커버리: 서비스 레지스트리가 각 서비스의 주소와 상태정보를 관리하고, 다른 서비스는 서비스 레지스트리에서 정보를 받아 올바른 서버로 요청을 보낼 수 있다
  - Consul
  - Etcd
  - Spring Cloud Eureka

## DB

- 수직 확장
  - DB 서버의 성능 추가
  - 다만, 물리적, 비용적 한계가 있음
- 수평 확장
  - Read Replica(읽기 복제)
  - 파티셔닝
  - 샤딩
- 분산 DB의 일관성
  - 강한 일관성: 복제가 완료될때까지 읽기 차단
    - 응답이 느리고, 가용성이 낮다
    - ex) 결제/이체, 포인트 등
  - 최종적 일관성: 모든 노드가 동일한 값을 갖게됨
    - 쓰기 직후 일시적으로 오래된 값을 조회하게 됨
    - ex) 좋아요/조회수, 배송 상태
- CAP 이론
- RDBMS
  - 인덱스
  - 트랜잭션 격리 수준
  - 쿼리 최적화 (EXPLAIN)
- Document DB
  - 자주 구조가 바뀌거나 읽기/쓰기가 많은 데이터를 위한 메인 DB
  - 유저 활동 로그, 상품 정보, 댓글/채팅메시지 등
- Key Value DB
  - 메모리 기반으로 읽기와 쓰기가 빠르다
  - 단순한 데이터를 위한 보조 DB
  - 로그인 세션 정보, API 응답 캐시, Pub/Sub 메시지 등

중요한건 만드려는 서비스에 맞는 DB를 선택하는 것이다. 각 회사의 상황에 맞게 결정하면 되는데 역시나 트레이드오프가 존재한다. 여러 DB를 활용하는 것보다는 하나를 선택하여 왜 그 DB를 선택하였는지 고민해보는 것이 중요하다. 초기 프로젝트에서는 그냥 RDBMS로 선택해도 무방하다

## 메세지 큐와 이벤트 브로커

- 메세지 큐는 Producer/Consumer 구조
  - 상품주문시 알림/이메일 발송 작업은 메세지큐에 넣고 순차적으로 처리할 수 있다
  - 장애가 발생해도 메시지는 안전하게 저장되어 유실없이 처리가 가능하다
  - 느슨한 결합 - 오직 메세지큐에만 의존하면 된다
- 이벤트 브로커는 Pub/Sub 구조
  - 상태변경을 데이터가 아닌 이벤트로 저장하여 복구로 재사용한다
  - 주문 상태 변경시 활용
  - 로그수집 (ELK 스택)

## 배치 처리와 스트리밍 처리

- 사용자 데이터를 정산하기 위해 보통 별도로 배치 프로젝트를 구성한다
- 배치 처리
  - 1시간이나 하루 단위로 데이터를 묶어서 처리한다
  - 데이터를 조회, 가공, 저장하는 일괄 처리 작업(ETL)
  - 실시간보다는 정확한 데이터를 안정적으로 처리하기 위함
  - Spring Batch, Apache Spark, cron, Jenkins 등
- 스트리밍 처리
  - 실시간으로 들어오는 데이터를 하나씩 처리한다
  - ex) 실시간 결제 이벤트를 소비하여 사용자에게 알림을 보내는 스트리밍 처리
  - Kafka, Redis, PULSAR, Spring Cloud Stream
